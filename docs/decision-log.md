# YouTube 字幕翻译扩展 - 决策日志

本文档记录项目开发过程中的重要技术决策、架构选择和设计变更。

## 架构与技术栈决策

### 1. 采用 Manifest V3 (2025-05-15)

**背景**：Chrome扩展平台逐步淘汰Manifest V2，新扩展需要采用V3架构。

**决策**：从项目开始即采用Manifest V3标准开发。

**理由**：
- 符合Chrome Web Store的未来要求
- 更好的安全性和隔离性
- 采用Service Worker替代持久后台页面
- 支持更现代的API

**影响**：
- 需要使用Service Worker作为后台脚本
- 功能实现方式与V2有区别
- 必须更谨慎地处理消息传递和长连接需求

### 2. 使用TypeScript作为开发语言 (2025-05-15)

**背景**：项目需要良好的代码组织和类型安全。

**决策**：采用TypeScript而非JavaScript开发。

**理由**：
- 静态类型检查减少运行时错误
- 更好的代码补全和开发体验
- 更易于维护和重构
- 更好的代码文档性

**影响**：
- 需要配置TypeScript编译
- 开发环境设置更复杂
- 需要定义接口和类型

### 3. 选择Vite作为构建工具 (2025-05-15)

**背景**：需要高效的开发和构建工具链。

**决策**：使用Vite而非Webpack进行项目构建。

**理由**：
- 更快的热重载
- 简化的配置
- 现代化的模块处理
- 内置TypeScript支持

**影响**：
- 需配置vite.config.ts支持多入口构建
- 使用vite-plugin-static-copy处理静态资源

## 核心功能实现决策

### 4. 字幕获取策略：主世界脚本注入 (2025-05-15)

**背景**：需要稳定获取YouTube字幕轨道信息。

**决策**：采用注入主世界脚本，通过postMessage通信方式获取字幕数据。

**备选方案**：
1. ❌ 直接在内容脚本解析`ytInitialPlayerResponse`（不稳定）
2. ❌ 使用MutationObserver监听DOM变化（复杂且不可靠）
3. ✅ 注入主世界脚本调用`getPlayerResponse()`API

**理由**：
- 主世界脚本能访问YouTube播放器JavaScript API
- 通过postMessage实现安全的跨环境通信
- 借鉴了成熟扩展（如Dualsub）的实现方式

**实现细节**：
- 通过web_accessible_resources暴露main-world.js
- 使用Promise封装异步消息通信
- 实现消息超时处理

### 5. 设置界面：使用Side Panel API (2025-05-15)

**背景**：需要用户友好的设置界面，避免过于侵入视频观看体验。

**决策**：使用Chrome的Side Panel API实现设置面板。

**备选方案**：
1. ❌ 覆盖在视频上的设置界面（干扰观看）
2. ❌ 弹出式窗口（体验割裂）
3. ✅ 侧边栏（不干扰观看，与YouTube界面协调）

**理由**：
- 侧边栏不会遮挡视频内容
- 用户可以随时打开/关闭
- 符合Chrome扩展的最新API发展方向

**实现细节**：
- 基于Chrome Side Panel API
- 使用基本HTML/CSS/TS构建界面
- 通过消息传递与内容脚本通信
- 在Service Worker中管理侧边栏可见性

### 6. 多翻译API支持策略 (2025-05-15)

**背景**：需要提供多种免费翻译服务供用户选择。

**决策**：实现多种免费翻译API接口，并提供简单的切换机制。

### 7. 翻译请求处理位置：Service Worker (2025-05-15)

**理由**：
- 规避内容安全策略(CSP)限制

## 存储与缓存决策

### 9. 字幕翻译缓存策略 (2025-05-15)

**背景**：频繁的翻译请求会导致API限流，影响用户体验。

**决策**：实现基于视频ID、目标语言和API类型的字幕翻译缓存。

**缓存键设计**：`subtitle_translation_cache_[videoId]_[targetLang]_[apiType]`

**理由**：
- 减少重复翻译请求
- 提高翻译响应速度
- 减轻API服务负担
- 在API暂时不可用时仍能提供服务

**技术实现**：
- 使用chrome.storage.local存储缓存
- 实现LRU（最近最少使用）清理策略
- 仅缓存翻译结果，不缓存源字幕

### 10. 设置存储分离 (2025-05-15)

**背景**：需要区分需要同步的用户设置和本地缓存数据。

**决策**：根据数据类型使用不同的存储区域。

**实现方式**：
- 用户偏好设置：使用chrome.storage.sync
- 缓存数据：使用chrome.storage.local

**理由**：
- 用户偏好应在不同设备间同步
- 缓存数据量大且设备特定，不需要同步
- 遵循Chrome存储最佳实践

### 13. 存储与状态管理优化策略 (2025-05-15)

**背景**：随着功能增加，存储和状态管理变得复杂，需要更结构化的方法管理数据流。

**决策**：实现全面的存储区域分离和状态管理架构。

**主要策略**：

1. **完全存储区域分离**：
   - 用户设置：使用`chrome.storage.sync`存储，键名使用`settings.`前缀
   - 字幕缓存：使用`chrome.storage.local`存储，键名使用`cache.`前缀
   - 会话数据：对临时状态使用`chrome.storage.session`，键名使用`session.`前缀

2. **存储访问层实现**：
   - 创建专门的存储访问模块，封装所有存储操作
   - 提供统一的读写API，隐藏底层存储机制细节
   - 实现存储监控，防止超出配额限制

3. **细粒度事件监听**：
   - 替换通用监听器，使用针对特定键和区域的筛选：
   ```typescript
   chrome.storage.onChanged.addListener((changes, area) => {
     if (area === 'sync' && changes['settings.subtitleMode']) {
       // 处理字幕模式变更
     }
   });
   ```
   - 将监听器按功能模块组织，避免单一大型回调

**理由**：
- 避免设置变更与缓存操作之间的干扰
- 提高存储操作效率
- 增强代码可维护性
- 简化调试和问题隔离

   - 实现发布/订阅机制

4. **TranslationDispatcher**：翻译调度器

### 16. TypeScript动态索引类型问题解决策略 (2025-05-25)

**背景**：在使用TypeScript处理对象动态索引赋值时，特别是在条件判断后，TypeScript类型推断系统会对变量类型作出限制性假设，导致类型错误。

**问题**：在`settings-manager.ts`中，当通过动态键访问并赋值`this.settingsCache[key]`时，出现类型错误：
- 将值赋给已被类型推断认定为`undefined`的属性时，出现错误
- 赋值的内容是`string | boolean | OpenAIConfig | CustomApiConfig | MembershipCredentials`类型，无法赋值给`undefined`类型

**决策**：采用`as any`类型断言统一处理TypeScript动态索引类型问题。

**备选方案**：
1. ❌ 修改`settingsCache`定义为索引签名类型（会影响类型安全）
2. ❌ 关闭`strictNullChecks`（降低整体类型安全性）
3. ✅ 在特定位置使用`as any`类型断言（局部解决问题）

**理由**：
- 类型断言提供了在保持大部分类型安全的同时解决特定问题的能力
- 一致性使用`as any`断言简化维护，易于识别这类特殊处理
- 对相似问题使用相同解决方案，减少混淆和不一致

**实施**：
- 在`settings-manager.ts`中特定位置使用`(this.settingsCache as any)[key] = value`形式
- 确保仅在必要位置使用类型断言，不滥用
- 在团队开发中统一使用这种模式处理类似问题

**影响**：
- 小范围内绕过TypeScript类型检查，可能引入类型相关错误
- 需要依赖开发者自律确保正确赋值
- 简化复杂对象操作，减少类型错误

**实现细节**：
- 在`settings-manager.ts`中特定位置使用`(this.settingsCache as any)[key] = value`形式
- 确保仅在必要位置使用类型断言，不滥用
- 在团队开发中统一使用这种模式处理类似问题

## 2025-05-27: 内容脚本构建策略变更 [TS]

### 背景
内容脚本在加载时遇到错误：`Uncaught SyntaxError: Cannot use import statement outside a module`。这是由于内容脚本使用了ES模块语法，但注入环境不支持ES模块。先前的解决方案尝试通过修改manifest.json的`"type": "module"`和改变代码中的导入方式解决，但这种方法不够彻底，问题仍然存在。

### 决策
**采用双重构建策略**，为内容脚本和其他脚本使用不同的输出格式：

1. 内容脚本使用IIFE（立即执行函数表达式）格式 - 将所有依赖打包到一个闭包中
2. 背景脚本、主世界脚本等继续使用ES模块格式

### 实现方式
1. 将构建过程分为两个阶段，使用mode参数区分：
   ```json
   "build": "npm run build:main && npm run build:content",
   "build:main": "vite build",
   "build:content": "vite build --mode content-script"
   ```

2. 在vite.config.ts中添加条件配置：
   ```typescript
   export default defineConfig(({ command, mode }) => {
     if (mode === 'content-script') {
       // 返回IIFE格式的内容脚本配置
     }
     // 返回ES模块格式的其他脚本配置
   });
   ```

3. 从manifest.json中移除content_scripts的`"type": "module"`属性

### 权衡
**优势**：
- 彻底解决了ES模块导入错误
- 保留了背景脚本等组件的ES模块优势
- 更符合Chrome扩展的最佳实践

**劣势**：
- 构建过程更复杂，需要两步构建
- 可能导致依赖重复，增加最终包大小
- 需要注意内容脚本与其他模块之间的通信方式

### 结果
这种方法解决了内容脚本加载问题，扩展功能正常工作，播放器控件能正确显示。

## 用户界面与交互决策

### 15. 语言搜索功能优化策略 (2023-06-10)

**背景**：用户需要在语言选择下拉菜单中快速找到目标语言，传统的前缀匹配搜索不够灵活，无法满足多样化的搜索习惯。

**决策**：实现多维度语言搜索机制，支持多种搜索关键词类型。

**支持的搜索关键词类型**：

1. **国际地区区号**：
   - 例如：`86`匹配中文(简体)、`81`匹配日语、`1`匹配英语
   - 针对用户熟悉国际电话区号的场景

2. **国家地区缩写**：
   - 例如：`CN`匹配中文(简体)、`JP`匹配日语、`US`匹配英语(美国)
   - 支持ISO国家代码，便于技术用户使用

3. **语言代码缩写**：
   - 例如：`zh`匹配中文、`en`匹配英语、`es`匹配西班牙语
   - 符合BCP 47语言标记标准，支持技术用户

4. **语言的本地/原生名称**：
   - 允许用户使用语言的本地名称进行搜索
   - 例如：输入`español`找到西班牙语，输入`日本語`找到日语

5. **语言的英文名称**：
   - 支持使用英文名称搜索
   - 例如：`Chinese`、`Japanese`、`Spanish`等

**实现细节**：
- 在`populateTargetLanguages`函数中扩展搜索逻辑
- 为特殊国家代码创建映射表，如`JP -> ja`(日语)
- 保持搜索结果相关性，避免匹配无关语言
- 确保搜索速度和响应性

**理由**：
- 适应不同用户的搜索习惯
- 减少用户寻找语言的时间
- 提高整体用户体验
- 支持国际化用户群体

**示例搜索映射**：
```json
{
  "jp": ["ja", "jpn"],      // 日本
  "cn": ["zh-Hans", "zh-CN"], // 中国(简体)
  "tw": ["zh-Hant", "zh-TW"], // 台湾(繁体)
  "kr": ["ko"]              // 韩国
}
```
