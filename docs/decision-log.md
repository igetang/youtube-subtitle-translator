# YouTube 字幕翻译扩展 - 决策日志

本文档记录项目开发过程中的重要技术决策、架构选择和设计变更。

## 架构与技术栈决策

### 1. 采用 Manifest V3 (2025-05-28)

**背景**：Chrome扩展平台逐步淘汰Manifest V2，新扩展需要采用V3架构。

**决策**：从项目开始即采用Manifest V3标准开发。

**备选方案**：
1. ❌ 继续使用Manifest V2（面临被淘汰风险）
2. ❌ 等待V3成熟后再迁移（错失开发时机）
3. ✅ 直接采用Manifest V3（面向未来的选择）

**理由**：
- 符合Chrome Web Store的未来要求
- 更好的安全性和隔离性
- 采用Service Worker替代持久后台页面
- 支持更现代的API

**影响**：
- 需要使用Service Worker作为后台脚本
- 功能实现方式与V2有区别
- 必须更谨慎地处理消息传递和长连接需求

### 2. 使用TypeScript作为开发语言 (2025-05-28)

**背景**：项目需要良好的代码组织和类型安全。

**决策**：采用TypeScript而非JavaScript开发。

**备选方案**：
1. ❌ 纯JavaScript开发（缺乏类型安全）
2. ❌ 使用JSDoc注释（类型检查不够严格）
3. ✅ TypeScript开发（类型安全+现代化工具链）

**理由**：
- 静态类型检查减少运行时错误
- 更好的代码补全和开发体验
- 更易于维护和重构
- 更好的代码文档性

**影响**：
- 需要配置TypeScript编译
- 开发环境设置更复杂
- 需要定义接口和类型

### 3. 选择Vite作为构建工具 (2025-05-28)

**背景**：需要高效的开发和构建工具链。

**决策**：使用Vite而非Webpack进行项目构建。

**备选方案**：
1. ❌ Webpack（配置复杂，构建较慢）
2. ❌ Rollup（功能相对单一）
3. ✅ Vite（现代化，快速，开发体验好）

**理由**：
- 更快的热重载
- 简化的配置
- 现代化的模块处理
- 内置TypeScript支持

**影响**：
- 需配置vite.config.ts支持多入口构建
- 使用vite-plugin-static-copy处理静态资源

## 核心功能实现决策

### 4. 字幕获取策略：主世界脚本注入 (2025-05-28)

**背景**：需要稳定获取YouTube字幕轨道信息。

**决策**：采用注入主世界脚本，通过postMessage通信方式获取字幕数据。

**备选方案**：
1. ❌ 直接在内容脚本解析`ytInitialPlayerResponse`（不稳定，YouTube可能随时变更）
2. ❌ 使用MutationObserver监听DOM变化（复杂且不可靠，性能影响大）
3. ✅ 注入主世界脚本调用`getPlayerResponse()`API（稳定，借鉴成熟方案）

**理由**：
- 主世界脚本能访问YouTube播放器JavaScript API
- 通过postMessage实现安全的跨环境通信
- 借鉴了成熟扩展（如Dualsub）的实现方式
- 相对稳定，不易受YouTube页面结构变化影响

**影响**：
- 通过web_accessible_resources暴露main-world.js
- 需要实现跨环境消息通信机制
- 需要处理消息超时和错误情况

### 5. 设置界面：使用Side Panel API (2025-05-28)

**背景**：需要用户友好的设置界面，避免过于侵入视频观看体验。

**决策**：使用Chrome的Side Panel API实现设置面板。

**备选方案**：
1. ❌ 覆盖在视频上的设置界面（干扰观看体验）
2. ❌ 弹出式窗口（体验割裂，无法与视频同时操作）
3. ❌ 嵌入YouTube页面的侧边栏（复杂且可能被YouTube阻止）
4. ✅ Chrome侧边栏（不干扰观看，与YouTube界面协调）

**理由**：
- 侧边栏不会遮挡视频内容
- 用户可以随时打开/关闭
- 符合Chrome扩展的最新API发展方向
- 提供足够的空间展示复杂设置选项

**影响**：
- 基于Chrome Side Panel API实现
- 需要管理侧边栏的显示状态
- 通过消息传递与内容脚本通信

### 6. 多翻译API支持策略与优先级 (2025-05-28)

**背景**：需要提供多种免费翻译服务供用户选择，确保服务可用性。

**决策**：实现多种免费翻译API接口，并建立明确的优先级顺序。

**API优先级顺序**（与README.md保持一致）：
1. **Google翻译**（推荐，无需密钥，质量稳定）
2. **有道翻译**（对中文支持良好，语言对覆盖广）
3. **微软/Bing翻译**（翻译质量高，多语言支持好）
4. **OpenAI**（需用户提供API密钥，质量最高但有成本）

**选择标准**：
- **免费API优先**：降低用户使用门槛
- **稳定性考虑**：选择服务相对稳定的提供商
- **语言覆盖**：支持更多语言对的翻译
- **质量平衡**：在免费和质量之间找到平衡点

**备选方案考虑**：
1. ❌ 仅支持单一API（可用性风险高）
2. ❌ 仅支持付费API（用户门槛过高）
3. ✅ 免费+付费混合策略（兼顾可用性和质量）

**理由**：
- 提高服务可用性和稳定性
- 不同API对不同语言有优势
- 当某API限流时可切换到其他API
- 为高级用户提供更高质量的选择

**影响**：
- 需要为每个API实现统一接口
- 需要添加批处理和延迟机制防止限流
- 需要实现API测试和自动故障转移功能

### 7. 翻译请求处理位置：Service Worker (2025-05-28)

**背景**：需要决定在内容脚本还是Service Worker中处理翻译请求。

**决策**：在Service Worker中处理翻译请求。

**备选方案**：
1. ❌ 内容脚本直接发送翻译请求（可能受到CSP限制，复杂度高）
2. ✅ Service Worker中处理翻译（更灵活且可规避CSP限制）

**理由**：
- 规避内容安全策略(CSP)限制
- 集中管理API调用逻辑
- 便于实现缓存机制
- 减轻内容脚本负担，提高页面性能

**影响**：
- 需要建立内容脚本到Service Worker的消息通信
- 翻译状态管理集中在Service Worker
- 需要处理Service Worker的生命周期问题

### 8. 字幕显示顺序优化 (2025-05-28)

**背景**：双语字幕的显示顺序影响用户体验和阅读效率。

**决策**：调整为目标语言（用户熟悉的语言）在上，源语言在下。

**备选方案**：
1. ❌ 源语言在上，目标语言在下（传统方式但不符合阅读习惯）
2. ✅ 目标语言在上，源语言在下（符合用户阅读习惯）
3. ❌ 用户自定义顺序（增加复杂度，大多数用户不需要）

**理由**：
- 符合自上而下的阅读习惯
- 减少认知负担，用户优先看到理解的语言
- 提高内容浏览效率
- 参考其他成熟字幕工具的做法

## 存储与缓存决策

### 9. 字幕翻译缓存策略 (2025-05-28)

**背景**：频繁的翻译请求会导致API限流，影响用户体验。

**决策**：实现基于视频ID、目标语言和API类型的字幕翻译缓存。

**缓存键设计**：`subtitle_translation_cache_[videoId]_[targetLang]_[apiType]`

**备选方案**：
1. ❌ 不使用缓存（每次都调用API，成本高且慢）
2. ❌ 仅基于视频ID缓存（无法区分不同语言和API）
3. ✅ 多维度缓存键（精确匹配，避免错误复用）

**理由**：
- 减少重复翻译请求，节约API成本
- 提高翻译响应速度，改善用户体验
- 减轻API服务负担，避免限流
- 在API暂时不可用时仍能提供服务

**影响**：
- 使用chrome.storage.local存储缓存
- 需要实现缓存清理策略
- 需要处理缓存版本和兼容性问题

### 10. 存储策略统一决策 (2025-05-28)

**背景**：项目初期考虑使用混合存储策略，但实际开发中发现统一存储更适合项目需求。

**决策**：统一使用chrome.storage.local作为主要存储方案。

**具体策略**：
- **翻译设置**：chrome.storage.local
- **翻译结果缓存**：chrome.storage.local  
- **视频特定设置**：chrome.storage.local
- **原字幕轨道信息**：Memory Cache（Background内存，会话级别）

**备选方案对比**：
1. ❌ 混合存储（sync+local）策略的问题：
   - 增加复杂度，需要维护两套存储逻辑
   - sync存储有配额限制，容易超限
   - 数据同步可能导致冲突和不一致
   - 用户设置与缓存数据边界模糊

2. ✅ 统一local存储的优势：
   - 简化存储逻辑，降低维护成本
   - 避免配额限制问题
   - 数据一致性更好
   - 更适合Chrome扩展的使用场景

**Memory Cache决策理由**：
- 原字幕轨道信息属于临时数据，页面刷新后需要重新获取
- 内存存储访问速度更快
- 减少不必要的持久化存储
- 符合数据的实际生命周期

**理由**：
- 简化架构设计，降低复杂度
- 避免跨存储区域的数据同步问题
- 更适合单设备使用的扩展特性
- 减少存储配额管理的复杂性

**影响**：
- 用户设置不会在不同设备间同步
- 存储管理逻辑更加统一
- 减少了存储相关的Bug可能性

### 11. UI按钮交互模式选择 (2025-05-28)

**背景**：点击翻译按钮时出现重复调用问题，需要设计避免事件循环的按钮交互模式。

**决策**：采用混合模式 - 翻译按钮(直接调用+事件通知)，设置按钮(纯直接调用)。

**具体实现模式**：
- **翻译按钮（复杂操作）**：直接调用 + 事件通知
  - 原因：翻译功能涉及多组件协调（UIManager、ControlPanel、翻译流程、字幕显示）
  - 避免事件循环：按钮点击→直接调用setTranslateActive()→发出跨组件通知事件
- **设置按钮（简单操作）**：纯直接调用
  - 原因：主要是UI控制，逻辑相对简单，无需复杂的跨组件协调
  - 简化逻辑：按钮点击→直接调用setSettingPanelOpen()→直接执行操作

**备选方案**：
1. ❌ 纯事件驱动（容易造成事件循环）
2. ❌ 纯直接调用（无法支持跨组件协调）
3. ✅ 混合模式（根据复杂度选择合适的方式）

**理由**：
- 避免重复调用：直接调用避免了"发事件→自己监听→重复执行"的问题
- 保持扩展性：复杂操作仍可通过事件让其他组件响应
- 职责清晰：按钮负责用户交互，事件负责跨组件通信
- 性能优化：减少不必要的事件传递，降低调用链复杂度

### 12. 集中式Background缓存管理策略 (2025-05-28)

**背景**：分散的缓存操作导致数据不一致和重复处理，需要统一的缓存管理方案。

**决策**：实现集中式Background缓存管理，所有缓存操作统一在Background Script中处理。

**架构设计**：
- **Memory Cache (Background内存)**：字幕轨道信息，生命周期为标签页会话
- **Local Storage (持久缓存)**：翻译结果、视频设置、全局配置  
- **API调用层**：最后兜底的数据获取

**备选方案**：
1. ❌ 分散式缓存（各组件独立管理）- 容易造成数据不一致
2. ❌ 纯ContentScript缓存 - 受到页面环境限制
3. ✅ 集中式Background缓存 - 统一管理，数据一致

**理由**：
- 数据一致性：统一的缓存管理避免数据冲突
- 性能优化：三层缓存策略最大化命中率
- 职责分离：Content Script专注业务逻辑，Background专注数据管理
- 可维护性：集中的缓存逻辑便于调试和优化

### 13. 语言冲突解决策略选择 (2025-05-28)

**背景**：当用户设置的源语言等于目标语言时，需要智能处理避免无意义的翻译。

**决策**：采用基于轨道检测 + 智能替换的组合策略。

**策略概述**：
1. **轨道分类**：将可用轨道按非ASR/ASR、非目标语言/目标语言四组分类
2. **自动选取**：优先选择非目标语言的非ASR轨道作为源语言  
3. **降级提示**：若仅有同语种轨道，显示"仅有{语言名}字幕，请先选择目标语"
4. **用户引导**：引导用户在侧边栏选择合适的目标语言
5. **缓存复用**：缓存最终的语言配置，避免重复处理

**备选方案**：
1. ❌ 直接禁用翻译功能（用户体验差）
2. ❌ 强制要求用户重新选择（增加操作复杂度）
3. ✅ 智能检测+用户引导（自动化+用户控制）

**理由**：
- 自动化程度高：能够智能选择最佳的源语言轨道
- 用户体验好：提供清晰的提示和引导
- 兼容性强：适用于各种语言组合和轨道情况
- 性能友好：缓存机制避免重复处理

## 架构修复决策 (2025-05-28)

### 14. Memory Cache vs Local Storage架构合规修复

**背景**：在架构审查中发现轨道数据存储位置与设计不符，违反了架构文档要求。

**问题识别**：
- 架构设计：轨道数据应存储在Memory Cache（内存全局变量）
- 实际实现：轨道数据被错误存储到Local Storage
- 生命周期错误：临时数据被持久化存储

**决策**：修正轨道数据存储位置，严格按照架构设计实现。

**修复方案**：
- 实现真正的`MemoryCacheManager`类
- 轨道数据存储在Background Script内存中
- 页面导航时自动清空Memory Cache
- 修正数据生命周期管理

**理由**：
- 符合架构设计原则
- 数据生命周期更合理
- 避免不必要的持久化存储
- 提高数据访问性能

### 15. 函数命名一致性修复

**背景**：架构修复后发现函数名与实际功能不匹配，容易造成开发混淆。

**问题识别**：
- 函数名：`saveTrackLocalStorage`、`getTrackLocalStorage`
- 实际功能：操作Memory Cache而不是Local Storage
- 误导性：函数名与实际操作不符

**决策**：统一修正函数命名，确保名称与功能完全一致。

**修复方案**：
- `saveTrackLocalStorage` → `saveTrackMemoryCache`
- `getTrackLocalStorage` → `getTrackMemoryCache`
- 更新所有调用位置
- 同步更新日志信息

**理由**：
- 提高代码可读性和可维护性
- 避免开发者混淆
- 建立清晰的命名规范
- 减少后续开发中的理解成本

### 16. SidePanel冗余操作优化

**背景**：发现SidePanel组件存在冗余的系统调用，影响性能和职责分离。

**问题识别**：
- SidePanel重复获取UI语言信息，并进行变种匹配
- Background已完成相同的处理
- 违反了职责分离原则

**决策**：优化SidePanel职责，移除冗余操作。

**优化方案**：
- 移除SidePanel中冗余的`chrome.i18n.getUILanguage()`调用
- 建立明确的职责分离：Background处理数据逻辑，SidePanel专注UI显示
- 信任Background的处理结果

**理由**：
- 减少重复的系统API调用
- 职责分离更清晰
- 提高整体性能
- 简化组件逻辑

### 17. 翻译开关执行逻辑架构合规修复

**背景**：翻译开关点击后的执行逻辑与架构文档设计不符。

- 影响性能优化效果

**决策**：补充完整的Memory Cache检查逻辑，严格按照架构设计执行。

**修复方案**：
- 在`handleTranslationStartRequest`函数中补充Memory Cache检查
- 实现完整的三层缓存检查流程
- 确保架构文档与代码实现一致

**理由**：
- 符合架构设计要求
- 提高缓存命中率
- 改善用户体验
- 建立架构一致性标准

## 消息通信架构决策

### 18. 统一请求-响应管理架构重构 (2025-05-28)

**背景**：现有架构中存在双监听器问题，导致消息处理冗余和架构设计不一致。

**问题识别**：
- 在`initializeSidePanel`函数中使用临时监听器
- 主消息监听器无法处理此类消息
- 违反了统一消息管理的原则

**决策**：实施统一的消息请求-响应管理架构重构。

**新架构特点**：
- 创建`MessageRequestManager`核心组件
- 统一消息格式，支持请求-响应配对
- 单一主监听器架构
- 支持超时处理和错误传播

**备选方案**：
1. ❌ 保持临时监听器（架构不一致，维护困难）
2. ❌ 回调方式（容易造成回调地狱）
3. ✅ 统一请求-响应管理（架构清晰，易维护）

**理由**：
- 消除消息处理警告
- 统一异步请求管理机制
- 提高代码可维护性和扩展性
- 支持并发请求而不互相干扰

**设计原则**：
- **单一职责**：一个全局监听器处理所有消息
- **请求配对**：通过requestId实现异步请求的正确匹配
- **集中管理**：统一的超时和错误处理机制
- **向后兼容**：不影响现有功能和无requestId的消息

### 19. 开发优化建议评估与筛选原则 (2025-05-28)

**背景**：在制定各类优化方案后，需要建立评估标准避免过度工程化。

**决策**：建立系统性的优化建议评估框架。

**评估标准**：

### 15. 按钮状态同步架构：Session Storage + 防抖机制 (2025-05-30)

**背景**：需要实现跨YouTube标签页的翻译按钮和设置按钮状态同步，确保用户在多标签页环境下有一致的操作体验。

**决策**：采用Chrome Session Storage + 防抖同步机制实现按钮状态的跨标签页同步。

**备选方案**：
1. ❌ 使用chrome.storage.local（生命周期过长，Chrome关闭后仍保留状态）
2. ❌ 纯Memory Cache（无法跨标签页共享）
3. ❌ 使用chrome.storage.sync（同步到云端不必要，且有配额限制）
4. ✅ 使用chrome.storage.session（会话级生命周期，完美匹配需求）

**技术特性**：
- **存储生命周期**：Chrome会话级别，Chrome关闭后自动重置为默认值
- **作用域**：跨所有YouTube标签页共享
- **默认状态**：翻译按钮和设置按钮默认为false（关闭状态）
- **防抖优化**：100ms延迟批量处理，避免高频操作

**理由**：
- **生命周期匹配**：Chrome关闭后重置，下次启动按钮回到默认状态，符合用户预期
- **跨标签页同步**：原生支持跨标签页状态共享，无需额外同步机制
- **性能优势**：Session Storage读写极快，100ms防抖避免高频操作
- **简化冲突处理**：采用"最后操作优先"策略，无需复杂时间戳判断

**冲突处理策略**：
```typescript
// 简化的冲突处理 - 去除时间戳机制
interface ButtonStateMessage {
  action: 'buttonStateChanged';
  updates: Record<string, boolean>;  // 直接传递最新状态
}
```

**防抖机制设计**：
- **防抖延迟**：100ms（用户无感知，但有效合并操作）
- **批量处理**：合并100ms内的多次按钮操作为一次同步
- **精确广播**：仅向YouTube标签页发送消息，避免无效通信

**影响**：
- 需要在Background Script中初始化session storage默认值
- Content Script需要监听并处理按钮状态变更消息
- UIManager集成ButtonStateSyncManager进行状态同步
- 性能开销极低（< 1KB内存，< 200ms同步延迟）

**验证标准**：
- ✅ Chrome启动时按钮默认为关闭状态
- ✅ 用户在标签页A操作按钮，标签页B实时同步状态
- ✅ Chrome关闭重启后按钮状态重置为默认值
- ✅ 100ms内的重复操作被正确合并
- ✅ 仅YouTube标签页接收状态同步消息

## SidePanel架构设计决策 (2025-05-30)

### 13. SidePanel数据结构设计：上下文模式

**背景**：SidePanel需要显示视频信息、用户设置、语言状态等多种数据，需要设计合理的数据传输结构。

**决策**：采用`SidePanelContext`统一上下文模式，包含videoId、tabId、globalSettings、detectedSourceLang、conflictState等核心数据。

**备选方案**：
1. ❌ 分散传输各个数据字段（通信复杂，状态不一致）
2. ❌ 传输完整的应用状态（数据冗余，性能影响）
3. ✅ 上下文模式（数据聚合合理，易于维护）

**理由**：
- 数据聚合程度适中，包含SidePanel所需的核心信息
- 便于版本控制和接口扩展
- 减少通信次数，提高性能
- 清晰的数据边界，易于测试和维护

**影响**：
- Background需要构建完整的SidePanelContext
- SidePanel接收单一数据源，简化状态管理
- 数据变更时需要重新构建完整上下文

### 14. 双向通信架构：双通道设计

**背景**：Background与SidePanel需要双向数据传输，既要传输业务数据，也要传输状态消息。

**决策**：采用双通道架构 - 主数据通道传输SidePanelContext，状态消息通道独立传输StatusMessage。

**备选方案**：
1. ❌ 单一通道混合传输（消息类型复杂，处理逻辑混乱）
2. ❌ 多个分散的通信通道（管理复杂，同步困难）
3. ✅ 双通道设计（职责清晰，易于维护）

**理由**：
- 业务数据与状态消息职责分离
- 状态消息更新频率较高，独立通道避免影响主数据
- 便于实现不同的消息处理策略
- 符合单一职责原则

**影响**：
- 需要实现两套消息处理机制
- StatusMessage支持独立的生命周期管理
- 可以针对不同通道优化传输策略

### 15. 语言冲突处理策略：单向解决原则

**背景**：源语言与目标语言可能发生冲突（如中文简体→中文繁体），需要确定冲突解决策略。

**决策**：只解决源语言冲突目标语言，不解决目标语言冲突源语言。当检测到同族语言冲突时，自动将目标语言切换为'auto'。

**备选方案**：
1. ❌ 双向冲突解决（逻辑复杂，用户困惑）
2. ❌ 禁止冲突选择（限制用户操作自由度）
3. ❌ 用户手动解决（增加操作负担）
4. ✅ 单向自动解决（简化逻辑，符合使用习惯）

**理由**：
- 用户通常是先看到源语言内容，再选择翻译目标
- 源语言通常是检测得出的，目标语言是用户选择的
- 自动切换到'auto'是最安全的降级策略
- 减少用户认知负担和操作复杂度

**影响**：
- 语言冲突检测逻辑相对简单
- 需要实现isSameLanguageFamily()判断函数
- 状态机只需处理单向解决流程

### 16. 多标签页同步策略：按需加载原则

**背景**：用户可能同时打开多个YouTube标签页，SidePanel需要根据当前活跃标签显示对应数据。

**决策**：采用按需加载策略 - 切换到哪个标签页就重新构建该标签页的SidePanelContext。

**备选方案**：
1. ❌ 预缓存所有标签页数据（内存占用高，复杂度大）
2. ❌ 智能预测缓存（过度工程化，收益不明显）
3. ✅ 按需加载（简单直接，性能可控）

**理由**：
- 大多数用户不会频繁切换标签页
- 0.1-0.3秒的加载延迟用户可以接受
- 避免复杂的多标签页状态同步逻辑
- 内存占用最小化

**影响**：
- 标签页切换时需要重新计算所有状态
- Background需要监听标签页切换事件
- SidePanel可能有短暂的加载状态

### 17. OpenAI配置处理：弹窗验证模式

**背景**：OpenAI等服务需要用户提供API密钥和选择模型参数，需要设计用户友好的配置流程。

**决策**：采用弹窗配置+自动验证+translationService测试的完整流程。用户选择OpenAI服务时自动弹出配置窗口，填写完成后自动验证参数完整性并进行translationService连接测试。

**备选方案**：
1. ❌ 内联配置（占用SidePanel空间，界面拥挤）
2. ❌ 分步配置（流程分散，用户体验差）
3. ❌ 延迟验证（可能在关键时刻发现配置错误）
4. ✅ 弹窗即时验证（集中配置，即时反馈）

**理由**：
- 配置流程相对复杂，弹窗提供足够的交互空间
- 即时验证避免用户在翻译时才发现配置错误
- translationService测试确保配置有效性
- 良好的用户反馈机制

**影响**：
- 需要实现模态弹窗组件
- 需要完善的表单验证逻辑
- 需要处理translationService测试的异步流程

### 18. 状态机驱动的冲突处理：确定性状态管理

**背景**：语言冲突检测和处理涉及多个状态转换，需要确保逻辑的可预测性和可测试性。

**决策**：采用状态机模式管理语言冲突处理流程，定义明确的状态（IDLE、DETECTING、CONFLICT_FOUND、RESOLVING、RESOLVED、ERROR）和转换条件。

**备选方案**：
1. ❌ 简单的if-else逻辑（难以维护，状态不明确）
2. ❌ 事件驱动处理（过于复杂，调试困难）
3. ✅ 状态机模式（状态明确，逻辑清晰）

**理由**：
- 状态转换逻辑清晰可预测
- 便于测试和调试
- 易于扩展新的冲突处理策略
- 符合DDD（领域驱动设计）原则

**影响**：
- 需要定义完整的状态机类
- 所有冲突处理必须通过状态机
- 便于监控和日志记录

### 19. 下拉列表互锁：数据预处理策略

**背景**：源语言与目标语言下拉列表需要互锁，避免用户选择冲突的语言组合。

**决策**：Background预处理互锁数据并传递给SidePanel，包含已禁用的选项和禁用原因，SidePanel直接使用预处理结果。

**备选方案**：
1. ❌ SidePanel自己计算互锁逻辑（重复计算，逻辑分散）
2. ❌ 实时查询互锁状态（增加通信开销）
3. ✅ Background预处理（集中逻辑，性能最优）

**理由**：
- 业务逻辑集中在Background，便于维护
- SidePanel专注于UI展示，职责单一
- 减少重复计算，提高性能
- 便于统一的语言处理规则

**影响**：
- Background需要实现语言互锁计算逻辑
- SidePanelContext需要包含互锁状态数据
- SidePanel的下拉列表组件需要支持禁用状态显示

### 20. 插件初始化预加载：分层数据准备

**背景**：插件首次加载时需要为SidePanel准备初始数据，包括全局设置、视频信息、语言检测等。

**决策**：采用分层数据准备策略 - globalSettings从storage加载，detectedSourceLang根据local/cache匹配，conflictState根据语言关系计算。

**数据准备优先级**：
1. **globalSettings**: 优先从local storage加载，无则使用默认值
2. **detectedSourceLang**: local完全匹配 > cache匹配 > 'auto'
3. **conflictState**: 如果detectedSourceLang不是'auto'则计算冲突，否则为空

**备选方案**：
1. ❌ 延迟加载所有数据（SidePanel初始状态空白）
2. ❌ 立即进行API调用获取数据（可能不必要的开销）
3. ✅ 分层准备（平衡性能和用户体验）

**理由**：
- 为用户提供尽可能完整的初始状态
- 避免不必要的API调用
- 利用已有的缓存数据提高响应速度
- 确保SidePanel有有意义的初始显示

**影响**：
- Background初始化逻辑相对复杂
- 需要实现数据匹配和fallback逻辑
- 可能需要处理数据不一致的情况
